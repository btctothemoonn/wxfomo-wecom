# wxFomo 量化信息流产品与数据口径 v1.1

> 状态基于 2026-09-02 的当前代码审查。这里的“已实现”表示仓库中已有对应代码；本文档没有把它等同于真实企业微信群环境中的全量或长期稳定验证。

## 1. 目标与基本判断

量化可以让“我漏看了什么、哪些群突然变密集、哪些消息值得回看”更可操作，但**指标变多不等于信息更完整或判断更准确**。wxFomo 的统计单位只能是“本机已经采集并落库的一条消息事件”，不是企业微信服务器中的原始消息。

第一版目标：在一个明确、可复现的消息范围内，先给出确定性统计，再由用户主动冻结实际消息集合并调用 AI；任何摘要、结论、提醒都能回到具体 `eventID`。

## 2. 已确认的来源边界

| 已确认事实 | 数据含义 |
| --- | --- |
| 默认来源是 macOS Notification Center 数据库中的官方企业微信通知，按企业微信标识、群白名单和事件指纹读取 | 统计的是系统实际投递并被 wxFomo 采集到的通知 |
| 默认路径不是 OCR、企业微信官方 API、私有数据库解密或进程 Hook | 不能据此推断企业微信服务器端的原始消息总量 |
| 免打扰、前台抑制、专注模式、隐藏预览、权限中断、通知清理和客户端版本变化都可能造成缺失或降质 | “已采集数下降”可能来自采集条件变化，而非群内真实流量下降 |
| `observedAt` 是本地通知记录/观测时间 | 不能宣称是企业微信消息的精确发送时间 |
| 群主要由通知中的显示名称标识，缺少稳定群 ID | 同名群可能被合并，改名可能被视为另一个群 |
| 发送者优先使用稳定 ID；没有稳定 ID 时使用显示名；两者都没有时记为未知 | “发送者键数”不是群成员数或真实发言人数，昵称可能重复、变化 |
| 媒体通知可能只有 `[图片]` 等预览文字；只有 payload 携带可用本地附件时才能打开原文件 | “媒体占位”不是图片丢失率，也不能反推出原媒体数量 |
| `eventID` 在本地消息库中唯一，重复事件不会重复入库 | 可以作为冻结、引用、告警和自动化幂等的本地主键 |

所有仪表盘、导出和 AI 结果都应使用“已采集消息/已采集通知”措辞，并显示来源边界。

## 3. 唯一的数据主路径

```text
选择时间区间 [start, end)
        ↓
构造同一个 MessageScope（群、类型、关键词、发送者、标签、查看游标等）
        ↓
SQLite 对该 Scope 做确定性量化，不依赖 UI 当前加载了多少页
        ↓
用户选择“分析当前已显示”或未来明确选择“分析全部匹配”
        ↓
把实际 eventIDs 冻结为不可变范围，并保存当时的 MessageScope
        ↓
用户主动提交 AI 任务；后台任务只读取冻结集合
        ↓
摘要、主题和发现引用 sourceMessageIDs，可回溯原消息
```

约束：

- 时间范围统一为左闭右开 `[start, end)`，避免相邻区间重复计数。
- 列表、统计和趋势必须复用同一个 `MessageScope` SQL 谓词；分页游标不属于业务 Scope，不能改变总数。
- 当前 AI 入口冻结的是点击时**已经显示的消息 ID**，不是自动把整个时间区间都送给 AI。只要还有分页，界面就必须明确写“已显示 X / 匹配 Y，分析 X 条”。
- 冻结后以 `eventIDs` 为事实来源，后续筛选变化、标签变化或新消息到达都不能改变该次分析输入。
- 默认区间分析必须由用户主动提交。规则中的 `enqueueSummary` 是用户显式配置的自动化例外，结果应标记“规则自动触发”，不能伪装为手动分析。

## 4. 交付状态

### 已实现

- SQLite 消息持久化、`eventID` 去重、分页、全文检索、标签和逐群查看游标。
- `MessageScope` 及统一 SQL 谓词：群、半开时间区间、消息类型、搜索、发送者、包含/排除标签、包含/排除词、正文词、已知发送者、查看游标以及标签/关键词任一命中。
- 基于完整 Scope 的已采集数、群名数、可识别发送者键数、未知发送者消息数、媒体占位数、固定时长桶、峰值以及群/发送者/类型分布。统计查询不依赖当前 UI 分页量。
- 显式 `eventIDs` 冻结、持久 AI 任务队列、重试/取消、来源引用、事实/推测/不确定状态。当前仓库中已有 App 接线，但本文未重新做真实 Provider 的端到端调用验收；引用校验只能证明 ID 属于冻结集合，不能证明模型文本在语义上正确概括了来源。
- 规则引擎会产生结构化 trace 和动作 intent；App 已执行标签、重点、抑制、本地告警和显式配置的单条摘要排队。`invokeScript` 当前明确不执行。
- App 内告警持久化、冷却期合并、来源 `eventID`、未确认数和确认操作；它不是 macOS 系统通知。
- 跨群地址提醒：同一 `0x` / Solana 地址在滚动 24 小时内进入至少两个群时生成提醒，并保留群名、提及数和来源消息。
- Meme 观察工作台：用户可从消息、地址筛选、AI 分析和跨群提醒手动发起 GMGN 查询；支持 Solana、Ethereum、Base、BSC 与 Robinhood。
- 当前用户私有 Unix Domain Socket 的 Node.js 只读 NDJSON 实时事件桥。

### 本轮量化建设

- **已实现**：把“待查看”“当前重点率”和“抑制率”作为当前 Scope 下的独立指标，而不只作为视图入口。
- **已实现**：有明确起止时间时并列显示当前与前一等长区间的原始已采集数；采集健康历史不足时不显示百分比趋势。
- 增加群聊集中度、发送者集中度，并同时展示可解释的 Top 1/Top 3 占比。
- 为量化结果保存 `scopeFingerprint`、计算时间、桶宽和采集条件判定，方便复现和审计。
- 持久化并展示规则 trace、动作执行结果和失败原因；目前 trace 只在求值结果中存在，未形成可查询的历史审计记录。

### 后续

- 采集健康时间线：权限、监听启停、数据库重置、来源模式、客户端版本和已知异常区间。
- 基于持久 outbox/检查点的可靠 Node.js 消费；实时 Socket 继续只做低延迟提示。
- 为跨群地址提醒增加可配置窗口、地址静音和持久动作审计；当前固定为 24 小时窗口。
- 主题演化、重复信息簇等高级分析后置。这些结果必须保留算法版本、输入 ID 和置信边界，不能替代基础计数。
- 稳定群 ID 或稳定成员 ID 只有在来源确实提供并经过验证后才能启用；不能从显示名猜测生成。

## 5. 第一版指标定义

设 `M(S)` 为同一个 `MessageScope S` 命中的已落库、按 `eventID` 去重的消息集合，`N = |M(S)|`。若 `N = 0`，比率显示 `0%`，集中度显示“无数据”；任何指标都应同时显示样本数 `N`。

| 指标 | 定义与公式 | 状态与解释 |
| --- | --- | --- |
| 已采集数 | `N = COUNT(M(S))` | **已实现**。只能叫“已采集”，不能简称“总消息”。 |
| 待查看 | 对每个群使用持久查看游标，`N_review = COUNT(m ∈ M(S_base) 且 order(m) > cursor(group(m)))`；没有游标的群，其匹配消息均为待查看 | **已实现**。独立指标排除已抑制消息；顺序使用统一的时间、来源序号和 `eventID` 规则，游标不能倒退。 |
| 重点 | `N_focus = COUNT(m ∈ M(S) 且 (有重点标签 OR 命中当前重点关键词))`；`R_focus = N_focus / N_unsuppressed` | **已实现**。这是当前规则配置下、非抑制已采集通知中的可审计命中率，不是 AI 判断的“价值”。 |
| 抑制率 | `R_suppress = N_suppressed / N_base` | **已实现**。用于观察规则降噪结果，不能解释为漏采率。 |
| 未知发送者消息率 | `U = COUNT(stableID 为空 AND displayName 为空)`；`R_unknown = U / N` | **已实现**。它衡量消息元数据缺失，不是“未知成员比例”。 |
| 媒体占位率 | `P = COUNT(messageType = media AND attachmentCount = 0)`；`R_placeholder = P / N` | **已实现**。分母是全部已采集消息；同时展示 `P/N`。不是图片失败率。 |
| 固定桶峰值 | 选固定秒数桶宽 `w`；`bucketStart = floor(observedAt / w) * w`；`B_k = COUNT(m ∈ [k*w,(k+1)*w))`；`Peak = max(B_k)` | **已实现**。桶宽从固定候选中自适应选择，目标约不超过 48 桶；桶与 Unix 时间对齐，不按本地日历/DST 拉伸。应补零桶或明确空档含义。 |
| 群聊集中度 | 对群显示名键计数 `n_g`，`p_g=n_g/N`；`HHI_group = Σ p_g²`；同时给出 `Top1/Top3 = Σ 最大 1/3 个 n_g / N` | **本轮**。`HHI` 越高表示采集样本更集中，但同名群合并会造成偏差。不要包装成好坏评分。 |
| 发送者集中度 | 已知发送者键为 `stableID`，否则为 `displayName`；排除未知桶，令 `K=N-U`，`q_s=n_s/K`；`HHI_sender = Σ q_s²`，`K=0` 时为“无数据”；同时给出 Top1/Top3 | **本轮**。未知消息率单列，避免把所有未知消息合成一个“人”而夸大集中度。仍然不是人数指标。 |
| 前一等长区间对比 | 当前区间 `I=[a,b)`，`d=b-a`，前区间 `I0=[a-d,a)`；复用完全相同的非时间 Scope，分别显示 `N` 与 `N0` | 原始计数对比**已实现**。健康历史尚不足以验证采集条件，因此当前不显示百分比或趋势结论。 |

### 等长区间的采集条件判定

百分比变化只有在以下信息足以支持可比时显示：两个区间都已结束；非时间 Scope、来源模式和群白名单一致；没有已知权限失败、监听中断、数据库重置或解码异常。还应记录应用/企业微信版本和监听健康摘要。

当前系统无法完整观测企业微信通知设置、专注模式和前台抑制，因此即使判定“可比”，也只能注明“未发现已知采集条件变化”，不能声称采集条件完全相同。若健康历史尚未落地，第一版应把可比状态标为“无法验证”，只并列显示 `N`、`N0` 和已知异常，不显示趋势结论。

## 6. 明确禁止的误导性指标

| 禁止名称/结论 | 原因 | 可用替代 |
| --- | --- | --- |
| 覆盖率、捕获率 | 缺少企业微信原始消息总数这个分母 | 已采集数、已知采集异常、来源说明 |
| 真实人数、活跃成员数 | 通常没有稳定成员 ID，显示名会重复或变化 | 可识别发送者键数、未知发送者消息率 |
| 完整群流量、群内总消息、真实增速 | 来源只包含系统实际投递的通知 | 已采集通知量、固定桶趋势、带条件的等长区间变化 |
| 综合价值分、信息质量总分 | 权重主观、来源不完整，AI 结果还受模型和提示版本影响 | 透明展示重点命中、集中度、告警数、AI 发现及其引用 |

如果未来确实需要排序，应展示各个可解释特征和规则版本，允许用户修改权重；界面不能把任意加权结果描述为客观“价值”。

## 7. 告警与规则 trace

- 规则求值必须保持纯确定性：输入为一条已落库消息和具体规则版本，输出 `status + reasons + actionIntents`。引擎本身不调用 AI、不发通知、不启动脚本。
- 本地告警是派生记录，不计入消息量。冷却期内合并时增加 `occurrenceCount`，保留来源 `eventIDs`，确认状态只改变工作流，不修改原消息。
- `enqueueSummary` 只能来自用户显式启用的规则，并记录 `ruleID/revision/actionIndex`、冻结范围和 Provider；它与用户手动区间分析分开统计。
- 当前规则只在新消息首次入库时求值；新建/修改规则不会自动回放历史消息，重复入库也不会重试此前失败的动作。没有持久动作账本前，不能宣称规则动作可靠执行。
- 本轮 trace 审计记录至少包含：`eventID`、`ruleID`、`ruleRevision`、求值时间、状态、reason codes、动作 intent、实际执行结果和脱敏错误码。规则关键词、群名和发送者名属于敏感配置，不应直接进入普通日志。
- 告警详情和 trace 必须通过 `eventID` 回溯本地消息；消息不存在时显示“来源已不可用”，不能展示无来源的确定性结论。
- `invokeScript` 在真正具备脚本注册、权限、超时、资源限制和审计前保持“不支持”，不能静默执行任意命令。

## 8. 跨群 CA/地址提醒与 Meme 查询（简单版，已实现）

### 8.1 用户目标

当同一个 `0x` 或 Solana 地址在多个已监听群的本机采集消息中出现时，在提醒中心生成一条“跨群地址出现”提醒。第一版只回答三个问题：哪个地址、出现在哪些群、对应哪些原消息。

“多个群出现”不等于项目可靠、价格将上涨或地址一定是代币合约。因此界面显示 DexScreener 已识别的具体网络；未识别的 `0x` 地址只显示“网络待识别”，Solana 格式地址显示“Solana”。没有链上验证时不写成“优质 CA”“热点币”或风险结论。

### 8.2 固定规则

- 复用本地确定性地址检测器，从每条成功入库的消息正文提取地址，不调用 AI。
- `0x` 地址使用小写作为聚合键；Solana 地址保持原始大小写。聚合键为 `family + normalizedAddress`；数据库内部为兼容历史数据，`0x` 地址族仍使用原始值 `evm`。
- 同一个规范化地址在滚动 24 小时内出现在至少 2 个不同群显示名中时触发。
- 同一地址只在同一群重复出现不会触发跨群提醒，但会增加该群的提及次数。
- 同一个 `eventID + normalizedAddress` 只记录一次，重复入库或重复求值不能增加计数。
- 已触发的地址继续出现时更新同一条活动提醒；连续 24 小时没有新提及后关闭本次活动周期，之后再次跨群出现可形成新提醒。
- 第一版不计算热度分、不判断买卖方向、不查询价格，也不区分机器人与真人转发。

24 小时是产品默认窗口，不是已验证的市场规律。后续如果真实使用表明过长或过短，再提供少量预设，而不是第一版就加入复杂参数面板。

### 8.3 持久数据

地址提及至少保存：

- `eventID`、地址原文、地址族、规范化地址
- 群显示名、发送者键（如有）、`observedAt`
- 创建时间以及检测器版本

跨群提醒至少保存：

- 地址族、规范化地址、首次与最近出现时间
- 不同群数、总提及数、群名列表
- 来源 `eventIDs`、确认状态、活动/关闭状态

建议索引为 `(family, normalizedAddress, observedAt)`，唯一约束为 `(eventID, family, normalizedAddress)`。App 升级后只回填最近 24 小时的已采集消息，避免启动时扫描全部历史。

### 8.4 界面

提醒列表使用一行紧凑展示：

```text
TOKEN · 示例代币 · Base
3 个群 · 7 次提及 · 最近 12:49
```

点击后按群展示来源消息；每条来源可跳回消息列表。提供复制地址、确认提醒和静音该地址三个动作。没有来源消息时明确显示“来源已不可用”，不能只保留一个无法验证的计数。

提醒可以使用普通、重要两档：首次达到 2 个群为普通；活动周期内达到 3 个群时升级为重要。升级只更新同一条提醒，不再创建重复记录。

### 8.5 已知边界

- 群按通知显示名区分；同名群可能被误合并，群改名可能被拆开。
- 通知未投递或未被采集的讨论不会进入统计，因此只能写“在 N 个已采集群显示名中出现”。
- 同一个 `0x` 字符串可能存在于不同网络，也可能是钱包地址；DexScreener 无结果或结果有歧义时保持“网络待识别”，不能根据地址格式猜成 Ethereum。
- 多群复制转发仍可能触发提醒。第一版接受这个限制，通过查看原消息和静音地址处理，而不是加入不可解释的评分。

### 8.6 验收例

1. 同一 `0x` 地址以不同大小写出现在两个群，产生一条提醒并保留两个来源。
2. 同一地址在一个群出现多次，不产生跨群提醒。
3. 同一地址第二个群的消息超过首条 24 小时，不与旧活动周期合并。
4. 同一事件重复处理不增加提及数；第三个群出现时原提醒升级而非新增。
5. Solana 地址按原始大小写匹配，普通长字符串不能进入地址提及表。
6. 点击提醒中的来源可以定位对应本地消息；来源缺失时显示不可用状态。

### 8.7 GMGN 查询边界

- GMGN 详情查询只由用户点击触发，不随企业微信消息自动请求；使用 20 秒超时与 45 秒本地缓存。
- Solana 地址按格式识别。完整 `0x` 地址会先通过 DexScreener 精确 token endpoint 查询，base/quote 任一侧命中均保留，并在支持链中按主池流动性、24 小时成交额排序；单链或明显领先的主池自动选择网络，多链信号接近时展示候选并要求确认。DexScreener 解析使用 8 秒超时与 120 秒本地缓存。
- `0x` 地址本身仍无法编码 Ethereum、Base、BSC 或 Robinhood；自动选择是基于当前 DEX 交易对的外部推断，不是链身份的数学证明。无交易对、服务失败或歧义时保留手动网络菜单。
- Robinhood 的支持范围是把 `robinhood` 作为 GMGN CLI 链参数查询；这不代表任何 `0x` 地址都属于 Robinhood，也不保证 GMGN 对目标地址已有数据。
- 行情、安全字段是外部瞬时快照；群聊统计仍只基于本机已采集通知，两者都不构成代币身份保证或投资建议。

## 9. Node.js 事件边界

当前事件桥的合同是低延迟、只读、尽力而为：

- 消息成功写入 SQLite 后才发布；发布发生在规则动作之前，所以 Worker 可能收到随后被规则抑制的原始事件。
- UDS 仅允许服务端发送版本化 NDJSON；客户端写入任何字节都会被断开。Socket/目录只对当前用户开放，但任意同用户进程都可能连接，“只读”不等于 Node 沙箱。
- Payload 含正文、群名、发送者和本地附件路径，Worker 必须视为受信任的本机代码；示例日志默认不打印这些敏感字段。
- `streamID` 每次 broadcaster 启动改变，`sequence` 只在该运行期内有序。未连接、断线或慢消费者被断开期间的事件不补发。
- Node 收到的事件数不能作为权威量化来源，也不能用于要求“不漏”的告警。权威计数来自 `MessageStore + MessageScope`。

后续可靠自动化应使用持久 outbox 或按 `eventID` 的只读查询与检查点，实现至少一次投递和消费端幂等；不得给 Worker 增加企业微信发送、回复、进程控制或消息库写权限。

## 10. 验收条件

1. **口径一致**：给定同一 `MessageScope`，分页加载方式不影响总数、桶、分布和集中度；列表全部分页的 `eventID` 集合与 Scope 冻结集合一致。
2. **边界一致**：所有时间过滤均为 `[start,end)`；相邻区间无重复；相同时间消息按统一规则稳定排序；查看游标不能倒退。
3. **指标可复算**：每张指标卡能看到 Scope 摘要、样本数、桶宽和计算时间；自动化测试覆盖空集合、全未知发送者、仅媒体占位、同桶边界及 `N0=0`。
4. **比较不越界**：采集条件无法验证或存在已知异常时，不显示百分比趋势，只显示原始计数和原因；任何地方都不出现“覆盖率、真实人数、完整群流量、综合价值分”。
5. **冻结准确**：提交 AI 前明确“已显示 X / 匹配 Y / 将分析 Z”；冻结的 `eventIDs` 与确认时的 Z 条完全一致，之后筛选或新消息不能改变输入。
6. **引用闭环**：AI 的摘要、主题和发现只引用冻结集合内的 ID；未知引用被拒绝或移除并产生验证警告；点击引用可打开来源消息。验收只覆盖引用完整性，不把它表述为语义真实性验证。
7. **规则可审计**：同一消息、同一规则版本重复求值结果一致；告警能回到来源；自动摘要标明规则触发；脚本动作显示未支持而非假成功。
8. **Node 边界可验证**：断线不阻塞采集，慢消费者会被隔离，重启后 `streamID` 改变且不承诺补发，客户端不能向 App 发控制命令。
9. **来源声明常驻**：量化页、对比页、AI 结果和导出均显示“仅基于本机已采集通知，不代表企业微信群完整消息流”。
10. **跨群地址可复算**：给定相同消息集合、检测器版本和 24 小时窗口，地址提及、不同群数和提醒来源完全一致；同群重复、重复事件和活动周期边界符合第 8 节规则。
